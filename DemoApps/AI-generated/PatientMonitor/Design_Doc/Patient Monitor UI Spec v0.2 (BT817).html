Bedside Patient Monitor UI: Engineering Design Spec v0.2 (BT817)

Display: 1280 × 800 LCD, landscape, always dark Graphics controller: Bridgetek BT817 (EVE4, capacitive touch) Supersedes: v0.1 (generic, browser-prototype-based) Sources: BT817/8 Datasheet v1.4 (BRT_000302), ME817EV datasheet. Items marked [verify] come from my general knowledge of the EVE programming model and must be checked against the BT81X Series Programming Guide before you build on them. Items marked (proposed) are design choices, not facts from the datasheet.

Regulatory note. The BT817/8 datasheet says the product is not intended for medical appliances or systems where a failure might reasonably be expected to cause personal injury, and puts use in safety applications at the user's risk. A bedside monitor is a medical device. Before committing to this part, get written confirmation from Bridgetek and your regulatory team of what use is acceptable, and add hardware and software safeguards (§9.4).

1. What changes from v0.1

The v0.1 spec assumed a general-purpose framebuffer (canvas drawing, 60 fps redraw of everything). The BT817 works differently, so several decisions change:

Topic v0.1 v0.2 (BT817)
Rendering Draw every pixel each frame BT817 renders from a display list, line by line. No frame buffer.
Waveforms Canvas line segments Per-lane byte arrays in RAM_G drawn as bar-graph bitmaps (§5)
Display list Unlimited 8 KB (2048 words) hard limit. Waveforms as vertex lists would overflow it
Fonts "Bundle locally" Custom fonts converted and stored in external NOR flash (§6)
Touch Generic BT817 capacitive engine with hardware tag lookup (§7)
Alarm audio Unspecified Built-in synthesizer plus AUDIO_L output, host-sequenced (§8)
Host Unspecified MCU over QSPI, up to 30 MHz (§9)

Confirmed from the datasheet

  • 1 MB integrated graphics RAM (RAM_G), no external frame buffer needed.
  • Host interface is SPI mode 0, single, dual or quad, up to 30 MHz. Quad mode is limited to half the system clock.
  • Display output is parallel RGB, 8 bits per channel maximum, panels up to about 1 megapixel and 2048 pixels wide. 1280 × 800 is listed as supported.
  • External QSPI NOR flash up to 2 Gbit for fonts and images, read directly by the chip.
  • Capacitive touch with up to 5 touch points and 255 hardware touch tags. Supported controllers are FocalTech, Hycontek and Goodix (plus host-driven "touch host mode").
  • Sound synthesizer and playback, mono sigma-delta output, PWM backlight output.

Panel interface. The chip outputs parallel RGB. If your 1280 × 800 panel takes LVDS, add an RGB-to-LVDS bridge (datasheet Fig. 7-2 shows an LVDS application circuit; Bridgetek's ME817EV eval board drives 40-pin LVDS panels up to 1280 × 800). The eval board is a good bring-up platform, and it carries 16 MB of NOR flash.

Take exact timings from the panel datasheet. The example below only shows the arithmetic.

Item Example Note

Constraints from the datasheet:

  • PCLK must not exceed 96 MHz, and PLL2 must not exceed 228 MHz.
  • When PCLK is equal to or above the system clock, set REG_PCLK_2X = 1. In 2X mode REG_HSIZE, REG_HOFFSET, REG_HCYCLE, REG_HSYNC0 and REG_HSYNC1 must be even, dithering is not applied, and HSF (non-square pixel filter) is unavailable.
  • At about 71 MHz PCLK this design will need 2X mode unless you can run PCLK below the system clock.

Line budget. The graphics engine runs the display list once per scanline. One line lasts about 1440 / 72 MHz = 20 µs, or roughly 1440 system clocks. That is the real limit on how much can be drawn on any one row. It is the main risk in this design (§10).

REG_UNDERRUN counts lines the engine failed to finish, and INT_UNDERRUN can interrupt the host. REG_ADAPTIVE_FRAMERATE (on by default) lowers the frame rate rather than corrupting the picture when a frame is too complex. Log both during validation. The shipping design should have zero underruns.

5. Waveform engine

5.1 Why not vertex lists

A 870-pixel trace drawn as a line strip needs about 870 vertices, so six lanes are about 5200 words. The display list holds 2048 words in total. Line strips are therefore only usable for heavily decimated traces.

5.2 Recommended method: hi/lo bar-graph pair per lane (proposed, [verify])

The engine supports a bar-graph bitmap format, where each byte in RAM_G is the height of one one-pixel-wide bar. Because sweep mode maps array index = screen x, this fits well:

  1. Per lane, keep two byte arrays of 870 entries in RAM_G: hi[x] and lo[x].
  2. For each new sample at column x, with y measured from the lane baseline, write hi[x] = max(y_prev, y) and lo[x] = min(y_prev, y). This joins consecutive samples, so steep edges such as the ECG R wave stay connected.
  3. Draw the hi bar graph in the trace color, then the lo bar graph in the background color over it. The visible band is the trace. Widen the band by 1 px for line thickness.
  4. For the erase gap, write hi = lo = 0 for the next 22 columns.
  5. For the CO₂ lane, draw only the hi array in the trace color for the filled-column look.

Because the lane background is black, the second pass can be opaque. If you add grid lines or a colored lane background later, use blend or stencil operations instead [verify].

Fallback. If the two-pass look is not right on the panel, decimate to about 100 to 150 points per lane and use line strips. That is roughly 900 words for six lanes, but it will look coarser.

5.3 Data rates and update path

Item Value
Sweep speed 150 px/s (≈25 mm/s, confirm against panel pixel pitch)
Samples per frame at 60 fps 2.5 px per lane
RAM_G used 6 lanes × 2 arrays × 870 B ≈ 10.4 KB (1% of 1 MB)
SPI traffic Tens of bytes per frame
  • Waveform arrays are updated by direct RAM_G writes. The display list is not rebuilt for waveform updates, and no CMD_SWAP is needed. The bitmaps are read on every scan.
  • Write new columns in ascending x order, ahead of the erase gap, so a mid-scan update is not visible as a tear.
  • Double-buffer on the host: build the column updates in MCU RAM, then send them in one SPI burst per frame.

5.4 Signal handling

  • Resample each source stream to 150 samples/s per lane on the MCU before writing.
  • Scale to the lane's configured min/max, clamp to 0 to 255 (lane height is 88 px).
  • On signal loss draw a flat baseline and show the technical alarm text in the lane.

6. Numerics, fonts and assets

6.1 Fonts

ROM fonts are limited in size and style. The condensed digits in the design (62 px and 48 px) need custom fonts (proposed):

  • Convert with Bridgetek's asset tools (EVE Asset Builder or the current equivalent [verify]) and store the font glyphs in external NOR flash.
  • Include only what is needed: digits 0 to 9, /, (, ), -, ., :, plus the label and unit characters. This keeps flash use small.
  • Use tabular (fixed-width) digits so a changing value never shifts neighbouring elements.
  • The chip reads glyph bitmaps straight from flash. This needs the flash to be in full-speed mode.
  • This also resolves the v0.1 concern about loading fonts from the internet: the fonts ship in the flash image.

6.2 Flash requirements (from the datasheet)

  • Flash must support XIP operation. Supported vendors include Cypress, Macronix, Winbond, Micron, ISSI and GigaDevice.
  • Program the 4 KB flash blob first, then call CMD_FLASHFAST to reach FLASH_STATE_FULL. Direct bitmap rendering from flash only works in that state.
  • After changing flash contents, call CMD_CLEARCACHE.
  • Read throughput is up to 288 Mbit/s at system-clock speed in 4-bit mode.
  • Store a version and checksum for the asset image, and verify at boot (§9.4).

6.3 Compression

ASTC is supported for images and large fonts. For photos or gradients it saves space, but at 8 × 8 block sizes it can soften small text. Use uncompressed L1, L4 or L8 glyph formats for the small text and ASTC only for large artwork (proposed).

7. Touch and soft keys

  • Use the BT817 capacitive engine with a supported touch controller (FocalTech, Hycontek or Goodix) on the panel's I²C touch module. Set the I²C address in REG_TOUCH_CONFIG to match the controller.
  • Run calibration once and store the transform (REG_CTOUCH_TRANSFORM_A to F) with the unit's settings.
  • Assign each key a hardware tag (1 to 255). The chip reports the tag under the touch point in REG_TOUCH_TAG, so the host never does hit-testing.
  • Use compatibility (single-touch) mode by default, since it is simpler and sufficient for keys. Use extended mode only if gestures are added later (proposed).
  • Key minimum size is 44 px high. Show a pressed state for at least 100 ms on tag press (proposed).
  • Keep the Silence key on a reliable path. Do not depend on a multi-step menu to reach it.
  • INT_TAG and INT_TOUCH can wake the host. Note that in extended mode the touch-down interrupt is not set, so use INT_CONV_COMPLETE instead.

8. Alarms and audio

Visual

  • Flash the alarming numeric using REG_MACRO_0 / MACRO(0) [verify]. The host toggles one register value at the flash rate, with no display list rebuild.
  • Show alarm text in the status bar with priority-based color.

Audio

  • The synthesizer includes alarm, beeping, warble, short-pip sequences (1 to 16 pips) and pitched MIDI-note effects. It can also play back samples from RAM_G (8-bit PCM, µ-law or IMA-ADPCM).
  • Output is a mono sigma-delta signal on AUDIO_L. It needs an external filter and amplifier (the ME817EV includes both for a 1/8 W speaker).
  • The host sequences the tones with REG_SOUND and REG_PLAY, and INT_SOUND signals the end of an effect.
  • The synthesizer does not by itself make the design compliant with any alarm standard (for example IEC 60601-1-8). Verify the melodies, timing, and sound pressure levels by measurement, and consider a dedicated audio path for high-priority alarms.

Logic stays on the host MCU: limits, priorities, silence timers, and latching. The BT817 only displays and sounds what the host tells it.

9. Host firmware

9.1 Boot sequence (from the datasheet)

  1. Power up: the chip starts in SLEEP. Hold PD_N low at least 5 ms if using it as a reset.
  2. Send CLKEXT if using an external clock, then ACTIVE.
  3. Wait for boot (up to 300 ms). During boot read only REG_ID (expect 0x7C) and REG_CPURESET.
  4. Set CLKSEL (in SLEEP only) if changing from the 60 MHz default, then update REG_FREQUENCY.
  5. Attach flash, run CMD_FLASHFAST, check REG_FLASH_STATUS.
  6. Program display registers (§3), then start with DISP low and REG_PWM_DUTY = 0.
  7. Load the first display list, wait for the first frame, then raise DISP and ramp up the backlight.
  8. Enable quad SPI (REG_SPI_WIDTH) once basic bring-up works. Note that host commands are only accepted in single-channel mode.

9.2 Frame loop

every frame (60 Hz, paced by INT_SWAP or a timer)
  1. read new samples, build hi/lo column updates
  2. write columns to RAM_G           (~tens of bytes)
  3. service touch tag, keys, alarms
every 1 s or on change
  4. rebuild display list (numerics, alarm state), CMD_SWAP
  • Command FIFO is 4 KB. Use REG_CMDB_SPACE to check free space, and do not overrun.
  • Keep waveform writes independent of display list rebuilds so a slow numeric update never stalls the sweep.

9.3 Backlight

REG_PWM_HZ (250 to 10000 Hz) and REG_PWM_DUTY (0 to 128). Start with about 2 kHz to avoid visible flicker on cameras (proposed), and check what the panel's LED driver accepts.

9.4 Safety and integrity (proposed, needs regulatory input)

  • Frozen-display detection. Read REG_FRAMES (frame counter) periodically. If it stops, restart the graphics engine or raise a technical alarm.
  • Render checks. REG_TAP_CRC gives a CRC of the live video output, computed on each display list swap. Investigate whether it can be compared with known-good values for static screens.
  • Underrun monitor. Alarm on a rising REG_UNDERRUN in service builds.
  • Asset integrity. Verify the flash image version and checksum at boot.
  • Independent alarm path. Audible alarms for high-priority conditions should not depend solely on the display chip working.
  • Watchdog. Host MCU watchdog resets the BT817 via PD_N, and reboot must restore a valid screen within a defined time.

10. Validation spikes (do these first)

# Spike Pass criterion
1 Six lanes with synthetic waveforms at 150 px/s, full-screen 60 Hz Zero REG_UNDERRUN; lines look connected and clean
2 Full numerics and chrome display list REG_CMD_DL below about 1800 words; zero underruns with spike 1 running
3 Custom fonts from flash at 62/48/44/30 px Readable at 3 m, no clipping, correct tabular alignment
4 Pixel clock: 2X mode at panel timings Stable picture, no edge noise (check REG_CSPREAD, drive strength via PINDRIVE)
5 Touch: tag reliability with the chosen panel All 14 keys hit correctly at edges
6 Alarm audio through the real amplifier and speaker Measured levels and patterns match requirements
7 Power cycle and brownout Valid screen returns within the target time; no garbage frame

If spike 1 or 2 fail, the fallback order is: (a) move static chrome into pre-rendered flash bitmaps, (b) drop the two-pass trace to a single-pass filled bar graph for the pressure lanes, (c) decimate to line strips, (d) reduce the resolution or refresh rate the design needs.
